## 2. 試合結果画面（公式スコアカード仕様）

### 2.1 ビジュアルコンセプト ＆ デザイン原則
他画面（通常オーダー、練習、大会進行、記録室等）と統一された**「白基調（ライトテーマ）」**の清潔感・公式記録感を追求。

| **背景色** | `#f4f6fa`（淡いニュートラルグレー） | 目に優しく、白カードの浮き上がり（立体感）を強調。 |

## 5. 「名場面」自動判定アルゴリズム（WPA ＆ LIロジック）

本作では、「なんとなくホームランが出たから」といった曖昧な抽出ではなく、セイバーメトリクスの客観的指標である **WPA（Win Probability Added: 勝利確率変動値）** と **LI（Leverage Index: 局面緊迫度）** を用いて、プログラムが定量的・科学的に名場面を自動判定・ランキングします。

### 5.1 WPA（Win Probability Added: 勝利確率変動値）による判定
打席が発生する前の自チーム勝率 $P_{\text{win}}(S_{\text{before}})$ と、打席結果が出た直後の勝率 $P_{\text{win}}(S_{\text{after}})$ の差分を算出します。

$$WPA = P_{\text{win}}(S_{\text{after}}) - P_{\text{win}}(S_{\text{before}})$$

- **勝率モデル $P_{\text{win}}(S)$**:
  - 状態 $S = (\text{イニング } I, \text{表裏 } B, \text{点差 } \Delta R, \text{アウト数 } O, \text{走者配置 } R)$
  - 過去数万試合のシミュレーションデータから構築された「勝率期待値マトリクス」を参照（ミリ秒で計算）。
- **抽出閾値**:
  - $|WPA| \ge 0.15$（1打席で勝率が **15%以上** 変動したプレー）を名場面候補として自動ピックアップ。
  - 例: 7回裏 1点ビハインド 1死二塁から神崎の2ラン本塁打：
    - 打席前勝率: $28\%$
    - 打席後勝率: $72\%$
    - $WPA = +0.44$（$+44\%$）➜ **本日の最重要名場面（CLUTCH OF THE GAME）に決定！**

### 5.2 LI（Leverage Index: 局面緊迫度）による判定
その局面がどれほど試合の勝敗に決定的な影響を与える場面であったかを示す指標です。

$$LI(S) = \frac{\mathbb{E}[|WPA| \mid S]}{\text{全試合・全打席の平均}|WPA|}$$

- **抽出閾値**:
  - $LI \ge 3.0$（平均的な打席の **3倍以上の緊迫度** を持つ局面）における好守・三振・併殺を抽出。
  - 例: 8回表 1点リード 1死一・三塁（$LI = 3.8$）：
    - リリーフ松田が相手4番打者をフォークで空振り三振に仕留めたシーン（$LI \ge 3.0$ かつ $WPA = +0.18$）➜ **名場面として自動抽出！**

### 5.3 定性ドラマフラグ（ボーナス加点）
以下の特別なドラマ要素が発生した場合、優先順位スコアにボーナスが加算されます。
- `FLAG_WALK_OFF`（サヨナラ打・サヨナラ本塁打）: 優先度 **最上位（即時確定）**
- `FLAG_GAME_SET`（9回裏2死からの最後の打者アウト・ゲームセット瞬間）: 優先度 **高**
- `FLAG_FINE_PLAY`（守備AIによるダイビングキャッチ・フェンス直撃捕球・レーザービーム本塁補殺）: 優先度 **中**

## 6. 技術的実現方式（キーフレーム・スナップショット技術）

### 6.1 なぜ動画ファイル（MP4/WebM）を使わないのか？
ブラウザゲームにおいて動画を録画・エンコード・保存する方式には以下の致命的な欠点があります：
1. **CPU/GPU負荷**: Canvas動画キャプチャは試合中に激しいフレームレート低下（ラグ）を引き起こす。
2. **ストレージ・通信量**: 1シーン数十MBの動画ファイルはIndexedDBやFirestoreの容量制限を圧迫する。
3. **ロード待ち時間**: 試合終了後に動画をロードする待ち時間が発生し、テンポが損なわれる。
4. **アングル固定**: 録画された動画では、再生中にカメラ角度を変えることができない。

### 6.2 軽量JSONキーフレーム・スナップショット方式の採用
本作では、プレー中の**「初期状態パラメータ」と「打球・選手ベクトルのキーフレーム」のみをわずか約 2KB の軽量JSONデータとしてメモリに保持**します。

Three.js 3Dエンジンは、このJSONを読み込んでミリ秒単位で物理演算とアニメーションを再実行（決定論的リプレイ再生）します。

```

┌────────────────────────────────────────────────────────┐
│ ① 試合中の重要プレー発生（MatchEngine）               │
│    └─ WPA/LI判定で重要シーン判定 ➜ スナップショット生成│
└──────────────────────────┬─────────────────────────────┘
                           │ わずか 2KB のJSONデータ

┌────────────────────────────────────────────────────────┐

│    ├─ 選手状態（投手・打者・走者・野手9名の初期座標） │
│    ├─ 投球ベクトル（球種、初速、変化球パラメータ）     │
│    ├─ 打撃ベクトル（インパクト時刻、打球初速、発射角） │
```

### 6.3 データ構造定義（TypeScriptインターフェース）

```typescript
/**
 * 試合ハイライト用 軽量JSONスナップショット定義 (約2KB)
 */
export interface HighlightSnapshot {
  id: string;                      // クリップ固有ID (例: "clip_07_bottom_hr")
  matchId: string;                 // 試合ID
  title: string;                   // 表示タイトル (例: "7回裏 神崎 逆転2ラン本塁打")
  tag: 'HOMERUN' | 'CLUTCH_K' | 'FINE_PLAY' | 'GAME_SET';
  inning: number;                  // イニング (例: 7)
  isTop: boolean;                  // 表/裏 (false = 裏)
  scoreBefore: [number, number];   // 打席前スコア [自校, 相手校] (例: [3, 4])
  scoreAfter: [number, number];    // 打席後スコア [自校, 相手校] (例: [5, 4])
  wpa: number;                     // 勝利確率変動値 (例: +0.44)
  leverageIndex: number;           // 局面緊迫度 (例: 3.8)

  // 1. 球場・環境パラメータ
```
